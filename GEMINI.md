# Контекст та інженерний журнал проєкту «Zyma»

Цей файл є ультимативним інженерним журналом для кіберфізичної системи (CPS) «Zyma». Він містить повний системний контекст, архітектурні рішення, вимоги до розробки та детальний опис ключових механізмів відмовостійкості (Fail-Safe Architecture).

## 1. Академічний та проєктний контекст (Вимоги БКР)

- **Університет:** Національний університет "Львівська політехніка" (НУЛП).
- **Кафедра:** Комп'ютеризованих систем автоматики (КСА).
- **Спеціальність:** 122 "Комп'ютерні науки" (ОПП "Інтернет речей").
- **Тип проєкту:** Кіберфізична система (CPS) / Індустріальний Інтернет речей (IIoT) для ферментації комбучі.
- **Критична вимога до ПЗ:** Жодного ESPHome чи готових YAML-конструкторів. Тільки чистий об'єктно-орієнтований C++ (ООП) для побудови UML-діаграм та детального опису програмної реалізації в додатках до пояснювальної записки.
- **Стандартизація:** Схеми алгоритмів повинні відповідати стандарту ISO 5807-85.

## 2. Архітектура кіберфізичної системи (CPS)

### А. Рівень Edge-девайса (`zyma-spore`)
- **Залізо:** ESP-WROOM-32 (ESP32 Dev Module).
- **Платформа розробки:** PlatformIO (Arduino framework, мова C++ ООП).
- **Логіка мережі:** Асинхронне неблокуюче підключення до Wi-Fi та MQTT брокера з циклічним автореконектом.
- **Безпека:** Секретні дані (Wi-Fi, MQTT) ізольовані в `include/secrets.h` та заблоковані у `.gitignore`.
- **Прошивка:** Бездротова (Over-the-Air) за протоколом `espota` через зафіксований TCP-порт хоста (`8266` для основного вузла, `8267` для тестового).

### Б. Рівень Локального Сервера (`zyma-cortex`)
- **Залізо:** Raspberry Pi 3 Model B (1 ГБ RAM).
- **Операційна система:** NixOS (Декларативне керування через Flakes).
- **Роль у системі:** Локальний IIoT-хаб, брокер повідомлень (Eclipse Mosquitto), сервер збору та первинного аналізу метрик.
- **Оптимізація:** Використання ZRAM з алгоритмом `zstd` для мінімізації навантаження на RAM. Заборона важкого стеку типу Grafana/InfluxDB.

#### Python IIoT Hub (`kombucha-cortex/main.py`)
- **Стек:** FastAPI (Python), SQLAlchemy (ORM з asyncio), paho-mqtt (асинхронний клієнт).
- **База даних:** SQLite (`/opt/kombucha-cortex/kombucha.db`) для зберігання даних вузлів, партій ферментації, телеметрії та калібрувань. Автоматичне створення таблиць при старті.
- **MQTT Інтеграція:**
    - Підключення до локального брокера (127.0.0.1:1883).
    - Підписка на `kombucha/+/+` для прийому телеметрії та оновлень стану від ESP32 вузлів.
    - Обробка повідомлень у фоновому режимі з оновленням DB та розрахунком pH.
    - Механізм авто-зупинки ферментації при досягненні критичного pH (<= 3.6).
    - Моніторинг активності вузлів з переведенням в `OFFLINE` при бездіяльності (>30 секунд).
- **Web UI:**
    - Легкий односторінковий дашборд без Node.js залежностей.
    - Використання TailwindCSS (CDN) для стилізації, HTMX (CDN) для динамічних оновлень, Chart.js (CDN) для візуалізації даних.
    - Надає таблицю вузлів, детальний дашборд для кожного вузла з графіками, формами для керування партіями (старт/стоп) та калібрування pH.
- **Розрахунок Soft Sensor pH:**
    - Реалізовано асинхронний розрахунок pH на основі температури та часу ферментації з можливістю калібрування.

## 3. Інженерний журнал відмовостійкості (Fail-Safe Architecture)

### 3.1. Нейтралізація мережевої пастки ШІМ (Захист SIL-3)

**Проблема:** Критичною загрозою в системах з термічним контролем є "тепловий розгін" (thermal runaway), коли нагрівач (150 Вт) залишається увімкненим неконтрольовано. У нашій архітектурі такий ризик виникав під час виклику синхронних, блокуючих методів мережевого стеку (`WiFi.begin()`, `client.connect()`). Якщо підключення затягується (недоступність Wi-Fi, падіння брокера), основний потік виконання "зависає", і стан ШІМ-виходу, що керує нагрівачем, залишається незмінним, потенційно у 100% потужності.

**Рішення:** Впроваджено **безумовний механізм попереднього блокування (pre-blocking safety valve)**. За один такт до будь-якого виклику блокуючого мережевого методу система примусово встановлює нульову шпаруватість (duty cycle = 0%) на ШІМ-виході `GPIO 26`. Це гарантує, що нагрівальна платформа буде повністю знеструмлена на весь час, поки мережевий стек намагається встановити з'єднання. Цей підхід повністю усуває вразливість "холодного старту" та гарантує безпеку системи навіть у разі тривалих мережевих збоїв.

### 3.2. Математичний апарат обчислення PPM Етанолу (MiCS-5524)

**Проблема:** Аналоговий сенсор етанолу MiCS-5524 має нелінійну залежність опору від концентрації газу. Для точного розрахунку PPM (parts per million) необхідно знати базовий опір сенсора в чистому повітрі ($R_0$), який може дрейфувати. Крім того, на низьких концентраціях вихідний сигнал АЦП потрапляє в "мертву зону" біля нуля, що робить вимірювання нестабільними.

**Рішення:** Реалізовано багатоступеневий асинхронний процес обробки:

1.  **10х Асинхронний оверсемплінг:** Для фільтрації шумів АЦП виконується 10 швидких послідовних вимірювань, результат усереднюється.
2.  **Програмне затискання опору $R_s$:** Для обходу "мертвої зони" АЦП, розрахункове значення опору сенсора в чистому повітрі ($R_s$) програмно обмежується знизу на рівні **1 МОм**. Це створює стабільну "підлогу" для вимірювань.
3.  **Динамічне ковзне автокалібрування $R_0$:** Протягом перших 25 секунд після старту вузла система накопичує усереднені значення $R_s$ і розраховує стабільне значення $R_0$, яке і буде використовуватись для подальших обчислень.
4.  **Розрахунок PPM за степеневим наближенням:** Концентрація етанолу розраховується в реальному часі за формулою, отриманою шляхом логарифмічного наближення кривої з даташиту сенсора:
    $$ \text{ppm} = 10.0f \times \left( \frac{R_s}{R_0} \right)^{-1.48f} $$
    де $R_s$ — поточний опір сенсора, а $R_0$ — відкалібрований базовий опір.

### 3.3. Процесний Інтерлок та Валідація даних

**Проблема:** Збої на рівні окремих датчиків або втрата зв'язку зі SCADA-системою не повинні призводити до неконтрольованого продовження або зупинки технологічного процесу.

**Рішення:** Впроваджено кілька рівнів логічної валідації та блокувань:

1.  **Перевірка CRC8 для AGS02MA:** Дані від цифрового датчика TVOC (AGS02MA) приймаються тільки після успішної валідації контрольної суми за поліномом `0x31`. Це відсікає пошкоджені пакети, що виникають через шуми на шині I2C.
2.  **"Reality Filter" для датчиків Dallas:** Показання температури з датчиків DS18B20 проходять через фільтр реалістичності. Значення за межами діапазону **0...80°C** ігноруються як помилкові, запобігаючи неадекватній реакції регулятора.
3.  **Персистентний прапорець `processEnabled`:** Стан процесу (Run/Stop) зберігається в енергонезалежній пам'яті ESP32 (Preferences). Це означає, що навіть після повного перезавантаження вузла (збій живлення) система автоматично повернеться до того стану, в якому вона була до збою, і не запустить/зупинить процес без команди від SCADA-системи верхнього рівня.
